灵动 APIAPI 文档 · 左栏原型 v2（全类型）

全类型统一为「能力族 → 格式组 → 接口」

这一版的层级、命名、排序全部从参考图反推，并且每一层都必须有后端字段能真实支撑；没有支撑的层不画。

从参考图推导出的 6 条规则

规则推导依据（参考图）我方对应
R1 板块＝能力族 音频 / 聊天 / 补全 / 嵌入 / 图像 各自独立，一个板块只回答「我能调什么能力」 把「语言模型」拆成 聊天（Chat） + 补全（Completions）；「向量与检索」拆成 嵌入（Embeddings） + 重排（Rerank）
R2 板块名＝中文（English） 「音频（Audio）」「聊天（Chat）」「嵌入（Embeddings）」 板块名不再取模型广场的「××模型」，改用能力族名 + 英文；模型广场名称不受影响
R3 板块按英文名字母序 Audio → Chat → Completions → Embeddings → Images，不是按业务重要性 Audio / Chat / Completions / Embeddings / Images / Moderations / Music / Rerank / Videos
R4 第二层＝格式 「原生OpenAI格式」「原生Gemini格式」「原生Claude格式」——格式是组名，不是接口名 接口名里现有的「（Anthropic 格式）」「（传文件）」全部拆掉，格式上移到组名
R5 单接口折叠为叶子 「补全 → 原生OpenAI格式 POST」：组里只有一接口时，组本身画成一行（组名 + 方法徽标） 补全 / 嵌入 / 审核 / 重排 / 即梦格式 都是单接口 → 叶子行，不再多占一层
R6 组按归属方英文序 聊天下 Claude → Gemini → OpenAI；音频下 Gemini → OpenAI 图像：即梦（Jimeng）→ OpenAI；同一板块内「原生」不特殊优先
与参考图唯一不照抄的一点：没有「原生Gemini格式」。 参考图那家支持 Gemini 原生协议（/v1beta/models/{m}:generateContent）； 我方入站线格式只有两种：openai 与 claude（internal/pkg/wireformat/format.go:20-23）。 凭空加一组就是伪造能力，所以这一版不出现。等真的实现了 Gemini 入站协议再加组，一条数据的事。

当前存在的问题

只列有代码依据的；每条都能指到行。

P0 · 直接让文档说假话

编号问题依据与后果
P0-1 板块口径取的是「模型广场」分组，不是能力族 section.go:97 直接用 GroupOf(id).Name。于是「语言模型」里同时装着 chat 与 completions 两套协议，「向量与检索」里混着 embeddings 与 rerank，「音频模型」里同步 TTS 与异步音乐（音乐又另开板块）。用户找不到「嵌入」。
P0-2 没有「格式」这一层 CatalogEndpointGroup 只有 Endpoints（catalog.go:156-160），类型板块下 Name 被强制置空（endpoint_docs.go:356-358）。后端无法表达「这个能力有三套格式」，前端也只能平铺。
P0-3 格式被写进了接口名 「对话补全（Anthropic 格式）」（endpoints.go:214）、「图片编辑（传文件）」（:456）。参考图正好相反：格式是组名，接口叫本名。
P0-4 厂商私有字段平铺进通用接口 视频提交 20 个 vendor 字段（endpoints.go:592-634）、图片生成 16 个（:386-418）、音乐 2 个（:907-909）。没有格式组，这些字段只能挂在一张表里，对不支持的模型就是假话。
P0-5 三个字段是伪能力（全仓无实现） camera_control（endpoints.go:625，标注「可灵」）、volume / pitch（:827-828）在 adapters/ 与 service/task/ 里均无任何读取。可灵适配器连 metadata 都明确 400（duomiapi_kling.go:49-55），说明它也不认运镜字段。

P1 · 结构缺陷（不改就会返工）

  • 只有两层，一级 10 项、其中 8 项同类：sectionOrder（section.go:34-37）把 8 个模型板块与「开始使用 / 通用接口」并列，参考图用一个「AI 模型接口」容器把它们收起来。
  • 前端没有折叠与叶子两种形态：DocsSidebar.tsx:234 的 grp.name 只是静态小标题 .dc-side-sub-h，既不能折叠，也没有「组名 + 方法徽标」的叶子画法。
  • 没有「单接口折叠为叶子」的规则：补全 / 嵌入 / 审核 / 重排 / 即梦格式都只有一个接口，不折叠就会多出 5 个只含一行的可折叠节点。
  • 接口命名不成词表：图片生成 / 图片编辑（传文件）/ 图片变体 vs 生成图像 / 编辑图像 / 图像变体；文字转语音 vs 文本转语音；语音转文字 vs 音频转录；语音翻译成英文 vs 音频翻译。同一个动作在侧栏里两种叫法，「转录」和「转文字」用户会以为是两个能力。
  • 读面归属没规则：catalog.go:97 只取 groupKinds 的 main，查询 / 下载 / 取消不进目录。视频板块拆分后，读面到底跟「直挂统一入口」还是跟某个格式组，代码里没有判据。
  • 后端没有 dialects 这个事实：DocEndpointDoc 只有 Section 与 Group（model/doc_endpoint.go:30-36），而 Group 已经被「通用接口导航子组」占用且每次启动重写。复用它存格式会把板块归属覆盖掉，必须新增独立列。
  • 同路径的方言篇会撞主键（最容易被忽略的一条）：doc_endpoint_docs 主键是 endpoint_kind 单列（model/doc_endpoint.go:29-30），一个 Kind 只能有一篇文档。而 /v1/images/generations 与 /v1/video/generations 各要两篇（原生 / 即梦）。不把主键改成 (endpoint_kind, dialect)，这两处就只能二选一 —— 字段表必然对一半模型说谎。slug 也要跟着改：ep-images-generations 与 ep-images-generations--jimeng。

P2 · 一致性与去敏

  • 排序按 kind 声明顺序（endpointTable:195），不是「直挂 → 格式组」；图像板块会把异步提交混在同步接口中间。
  • 禁词与品牌命名冲突：参考图要求把「即梦 / 可灵 / SUNO」写进组名，而现有去敏表把这些词也一并禁掉。需要把「模型品牌（可写）」与「转发平台（Ark / 火山 / 方舟 / 多米 / metaso / AutoDL，不可写）」分开。
  • 模型文档与接口文档两套分组口径：模型文档按 vendor + 类型签名分桶，接口文档按 kind 一篇，同一家厂商在侧栏出现两种形状。

需要你拍板的 3 件事

① 视频的读面（查询 / 下载 / 取消）挂哪？
建议直挂板块，与「创建视频任务」同层（原型即此写法）。理由：读面与格式无关，任何格式创建的任务都走同一套查询，塞进某个格式组会让另外几组看起来没有查询接口。
② 同一条路径、两套报文（/v1/images/generations 与 /v1/video/generations）允许出现两次吗？
建议允许，靠父级格式组区分（原型里「生成图像」在即梦格式与原生OpenAI格式各出现一次）。代价是必须把 doc_endpoint_docs 主键改成 (endpoint_kind, dialect) 并给 slug 加 --jimeng 后缀 —— 这是本轮唯一一处要动主键的改动，不确认就不能动工。
③ 伪能力字段怎么处理？
建议从文档删除 camera_control / volume / pitch（代码里没有实现，写上就是骗人）；若确实要支持，走「先实现适配器 → 再进文档」。这一条会改 endpoints.go 三行，不影响计费。
