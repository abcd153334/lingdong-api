# 怎么把 JSON 写对

一次性手写几 KB、十几层嵌套的 JSON 是这类任务里最容易失败的一步。
失败有两种，**处置完全不同**：

- **写坏了**：括号/引号不配对（回执里是 `invalid character …` 或 `unexpected end of JSON input`）
- **写不完**：输出被长度上限截断（回执里是 `output_truncated`）

两种都不要原样重试——同样的长度、同样的深度，重试大概率还是错。

## 五条硬规则

1. **一次只送 1–2 个 operation**。先把「供应商 + 规格」写对，再追加渠道、模型、绑定。
2. **每个对象独立成行、缩进 2 格**。手写紧凑单行时，闭括号层数几乎必然数错。
3. **先把 `spec` 单独写对，再包进 `operations`**。`spec` 是全文最深的结构（端点 → body → copy），
   它错了整份都过不了。
4. **不要自己补 `}` 猜结尾**。宁可先交已经写好的部分，让服务端告诉你缺在哪一层——
   补错的括号会把「结构错」变成「结构对但内容错」，错误反而被推到更晚。
5. 参数体积控制在 4KB 内。超了不是"再挤一挤"，是**该拆**。

## 分块校验（`mode="shape"`）

`validate_draft` 有 `mode` 参数：

- `mode="shape"`：只校验 JSON 结构与 spec DSL 语法（不查库、不试跑、不检查跨操作引用）。
  用来确认"我这一段写对了"。
- `mode="full"`（默认）：完整预演，等价于 propose_change。

推荐节奏：`shape`（第 1 块）→ `shape`（第 2 块）→ 拼成一份 `full`。
`shape` 通过不代表 `full` 通过：跨操作规则（新建模型必须带绑定、`channel_key` 只能指向本提案新建的渠道）
只在 `full` 里检查。

## 失败回执怎么读

```json
{"ok":false,"code":"invalid_arguments","line":34,"column":18,
 "snippet":"…\"kind\":\"per_second\"…","hint":"失败点仍在 $.operations[0] 内部：这个对象多开了一层 {"}
```

按这个顺序看：**`line`/`column` 定位 → `snippet` 确认位置 → `hint` 判断成因 → `unclosed` 看还差哪几层**。

三种最常见的成因：

| hint 说 | 真实原因 | 改法 |
| --- | --- | --- |
| 结尾被截断，还差 N 个 `}` | 写到一半到了长度上限 | 分块，别重试 |
| 失败点仍在 `$.operations[0]` 内部，多开了一层 `{` | 闭括号多写了一个 | 回到那一层逐层核对，不要动别处 |
| 字符串没闭合 | 字符串里有真实换行 | 换成 `\n`，或删掉换行 |

## 不要做的事

- 不要把成品 JSON 抄进正文发给运营看（正文只写结论与理由）。
- 不要在失败后整份重写：上一版参数已作废，也很可能把已经正确的部分改坏。
- 不要用占位符（`"<运营提供>"`、`…`）凑数——那不是合法参数，交上去只会换来一次参数错误。
