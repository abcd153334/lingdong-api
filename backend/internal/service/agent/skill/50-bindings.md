# 绑定（model_bindings）

绑定回答一个问题：**这个模型能从哪些渠道出去**。它是在售判定的必要条件：
模型启用 + 存在启用绑定 + 该绑定渠道启用 —— 三者缺一，模型就不进目录、也不进文档。

## 写法的两种形态

- 本提案内新建的渠道：`channel_key`（指向那条 create channel 的 key）
- 已存在的渠道：`channel_id`

`channel_key` 与 `channel_id` 必须**且只能**给一个。

## `replace` 是整体替换

提交的集合就是最终集合。想加一条绑定，也要把原有的都带上。
`disable` 单条用 `model` + `channel_id`。

## 七条校验（违反会被拒，且错误定位到 bindings[i]）

1. `upstream_model` 必填（它是上游真名的唯一来源，留空会给上游发空 model）
2. 同一渠道只保留一条：**后出现的覆盖先出现的**（不是报错）
3. 渠道必须存在且未删除
4. 渠道必须处于启用状态（库里已有的存量绑定豁免这条）
5. 渠道适配器必须支持该模态（存量绑定同样豁免）
6. `weight` / `priority` 在 1..1000
7. 新建模型时至少一条 `enabled: true`；替换已有绑定时，「在售」模型不能被改成零可用

## 端点覆盖

模型声明的每个端点，至少要有一个**启用绑定**能承接。否则模型会出现在文档里、
门户也可见，但调用必然失败（且用户可能已被扣费）。

写 `endpoints` 之前先想清楚：这个上游真的支持那个端点吗？拿不准就留空——
留空会按模态派生默认端点，比写错安全。

## `warnings` 是非阻断告警：原样转述，不要自己改配置

`validate_draft(mode="full")` 成功时可能返回非空的 `warnings`，含义是
**配置已经合法、但首次调用可能失败**。典型内容是「该渠道承接不了这个模型」
（例如平台模型 ID 不在适配器的内置档案里，也没有配 `model_overrides`）。

处理方式：

- **原样转述**给用户，不要改写、不要折叠成「可能有点问题」。
- **不要**尝试自己写 `adapter_options` / `model_overrides` —— 服务端会硬拒
  （渠道私有配置的形状由适配器定义，模型写不出可校验的值）。
- 给用户两条可选动作：
  1. 把平台模型 ID 改成协议族内命名（`kling-*` / `seedance-*` / `gpt-image-*` /
     `nano-*` / `gemini-*-image` / `suno-*` / `chirp-*`），协议可零配置推断；
  2. 请管理员在渠道页按**平台模型 ID**（不是上游模型名）登记 override。
- `mode="shape"` 不查库、不做预检，它的 `warnings` 恒为空 —— 看到
  `warnings_note` 时要提醒用户还差一次 `mode="full"`，不要把「没告警」当成「一定可用」。
