# 出错之后怎么恢复

失败不是一种东西。先看回执里的 `code`，再决定动作 —— 三类失败的处置完全不同，
用错方向的表现是"越修越远"（改配置去修一个参数错，或者反过来）。

## 第一类：参数写错（你自己能改）

`invalid_arguments` / `missing_arguments` / `output_truncated`。

回执里带 `field`、`line`、`column`、`snippet`、`balance`、`unclosed` 与 `hint`：

- `unclosed` 说"没闭合到哪一层"，就补那一层，别动别处；
- `line`/`column` 指到哪就只看那里，**不要整份重写** —— 重写会换一个新的错，
  而你已经对了的部分白白冒险；
- `balance` 显示 `{` 比 `}` 多 N 个，就先数结尾；多开一层（`{{`）比少闭合更常见。

`output_truncated` 是"你的输出被长度上限截断"，不是"你写错了括号"：参数根本没收全，
重试同样大小还会被截断 —— 唯一出路是**拆小**。

## 第二类：目标状态不对（重新读，不要硬试）

`not_found` / `*_conflict` / `agent_proposal_stale`。

这类失败说明"库里的东西跟你以为的不一样"，改参数没有意义：
先 `*_get` 拿最新值与 `version`，再决定是更新还是新建。
`stale` 尤其不要重试同一份提案 —— 它基于旧数据，重试还是过期。

## 第三类：环境/凭据问题（停下来问运营）

`dry_run_blocked` / `dry_run_failed` / 401 / 403 / 超时。

- 401/403：密钥错或权限不足 —— 不要换参数重试，直接 `ask_user` 要正确密钥；
- 404：路径错 —— 回文档核对端点，不要猜；
- 超时：地址/网络问题 —— 报告现象，不要连续重试烧时间。

## 什么时候分块（最容易做错的一步）

满足任一条就先 `validate_draft(mode="shape")`，只送 1–2 个 operation：

1. 参数接近 4KB；
2. 嵌套超过 6 层（`operations → data → spec → endpoints → <键> → request_fields` 就已经 6 层）；
3. 一次要写 3 个以上实体。

shape 只验"结构与规格语法"，**跳过跨操作规则**（新建模型必须带绑定、`channel_key` 必须指向
本提案新建的渠道）。所以凑齐之后**必须再跑一次 `mode="full"`** —— 别把 shape 通过当成能提交。

## 什么时候换路径

- 同一工具、同一类错 2 次 → 换粒度（分块）或换工具；
- 3 次 → 说明缺的是**事实**（真实型号名、真实计费方式），去 `ask_user`，不要再猜；
- 连续失败被中止后，不要假装完成：说清卡在哪一步、缺什么、你已经确认了什么。

## 不要做的事

- 把上一版坏参数拿来微调当基线（原文已作废，会用同一个坏结构再错一次）；
- 把 `truncated: true` 的结果当完整结果（后面那截你没看到，结论可能正好相反）；
- 用"平台不支持"来掩盖自己的参数错（`submit_unsupported` 是给真实 L3 结论用的）；
- 重试一次失败的上游调用超过两次（同一条死路，越试越贵）。
